# LumenDrop — Design (2026-11-20)

## Intent
A simple, good-looking web app to move a file between two devices using only a screen and a camera, built on libcimbar. Two modes: **Send** and **Receive**. Code stays small and plain; the UI is modern. Works offline after the first visit (PWA).

## Goals
- Send: pick or drop a file → barcode animation fills the screen, with file name, size, Stop, and a photosensitivity warning.
- Receive: camera full screen with an aim guide and a % progress ring → on completion, stop the camera and offer **Save file** (and **Share** where supported).
- Deploy as one Go binary behind Caddy (Caddy terminates HTTPS — required for iPhone camera).
- Credit libcimbar visibly (app footer, README) and ship all required license texts.

## Non-goals
- No server-side file handling: the server only delivers the app. Transfers never touch it.
- No encryption, multi-stream big files, or SHA-256 display (PLAN.md "Ideas for later").
- No frontend framework or build step; no Fiber.

## Approaches considered
| Approach | Trade-off | Decision |
|---|---|---|
| **Go stdlib `net/http` + `embed`, behind Caddy** | One-file deploy, zero deps, ~small `main.go` | **Chosen** (user wants a single binary) |
| Caddy `file_server` only | Even less code, but deploys a folder | Rejected: user prefers one binary |
| Go + Fiber | Familiar to user, but adds deps; Caddy already covers compression/HTTPS/HTTP2 | Rejected: no benefit for static serving |

## Layout
```
main.go, go.mod            # embed web/, serve on 127.0.0.1:8080 by default
web/index.html             # home: Send / Receive
web/send.html, recv.html
web/css/style.css
web/js/ui.js, send.js, recv.js   # our code, written fresh against the WASM API (MIT)
web/vendor/cimbar/         # libcimbar v0.6.9 release files, byte-for-byte (MPL-2.0) + licenses + SHA256SUMS
web/manifest.json, icons
Caddyfile                  # example reverse proxy
LICENSE (MIT), README.md
```
`sw.js` is generated by Go at runtime: cache version = hash of embedded files; precache list = walk of embedded FS (`index.html` mapped to `./`).

## Key technical decisions
- Vendor upstream `cimbar_js.<stamp>.js/.wasm`, `send.<stamp>.js`, `recv-worker.<stamp>.js` unmodified (stamped names required by the worker's `importScripts`).
- Send runs upstream `Send` on the main thread; our `Report` object implements the 5 callbacks it calls.
- Receive: worker pool of upstream `recv-worker`; main thread does fountain decode + zstd decompress; mode auto-detect then lock; `VideoFrame`→`createImageBitmap` and `requestVideoFrameCallback`→`requestAnimationFrame` fallbacks; ~1920×1080 @15fps camera; backpressure cap.
- Barcode canvas is never styled (no radius/filters/overlays); fullscreen = fixed overlay, Fullscreen API as enhancement.

## Security
- Default listen `127.0.0.1:8080`; `http.Server` with timeouts; `http.FileServerFS` only.
- Headers: CSP (`script-src 'self' 'wasm-unsafe-eval'`, no inline scripts), `nosniff`, `Referrer-Policy: no-referrer`, `frame-ancestors 'none'`.
- Received file is untrusted: names shown via `textContent`; Blob is `application/octet-stream`, offered only via download/share, never opened in-app.
- No third-party requests (system fonts, no CDNs). `.wasm` MIME registered explicitly.
- Barcodes are not encrypted: anyone who can film the sender's screen can recover the file (documented).

- Not verifiable here: real iPhone/Android behaviour (M3), production HTTPS deploy (M5).
